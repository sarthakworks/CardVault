# Security model

## At-rest protection

The master passphrase is used only in memory. Android's native PBKDF2-HMAC-SHA-256 derives a 256-bit root with a random 32-byte salt and 600,000 iterations on a background thread. HKDF-SHA-256 separates payload and verification keys. Password character arrays/specifications, root material, derived verification material, and mutable session key buffers are overwritten when their work is finished.

New master and dedicated backup passwords allow 5-256 characters, including digits. This shorter minimum does not weaken the encryption algorithms or reduce the KDF iteration count, but short passwords, especially five-digit numeric choices, are substantially easier to guess offline. Longer passphrases are strongly recommended. Existing passwords and backup decryption credentials are unchanged.

The encrypted verification token binds the vault identifier. AES-256-GCM authenticates both the verifier and the complete vault snapshot. Every encryption uses a fresh 96-bit nonce and 128-bit tag. Authenticated additional data binds the format, KDF parameters, vault identifier, purpose, scope, and revision through a fixed array encoding.

Vault records reach SQLite only as ciphertext and public headers. Card/note fields, record timestamps, and searchable content are not stored in plaintext columns, journal entries, or indexes. UI preferences and saved-backup file metadata (document names, URIs, location labels, sizes, and when they were added) remain unencrypted. Do not include sensitive information in backup filenames. Format metadata, ciphertext size, revision, and the existence of a vault remain observable.

Notes contain only a title and body, plus system identifiers/timestamps. No note-category or tag field is accepted into the runtime model or new snapshots. Loading an older authenticated snapshot strips that unknown metadata while preserving its text; no backup format or encryption change is required. A note may have no title or no body, but cannot be completely blank.

Card values are user-controlled, not verified payment credentials. New-card and edited-card writes share a schema requiring 13-19 numeric PAN digits, 3-4 numeric CVV digits, and a valid current/future expiry month. The editor uses numeric input and inserts the expiry separator; the service applies the same checks before accepting a new or edited record. Manual entry and persistence do not require Luhn or card-network-specific PAN/CVV matching. Camera OCR uses Luhn only as a candidate-selection heuristic before editable review, not as evidence of ownership or card validity.

Stored-record and backup schemas deliberately remain compatible with older free-form and expired card data, while enforcing required fields, bounded text, identifiers, and resource-size limits. Network/type values are editable text, not an enum-only assertion about verified payment credentials; older supported labels remain valid. Entry-time date checks are never applied to unlocking, importing, or whole-snapshot validation: otherwise the passage of time or one older record could make the entire vault unreadable or prevent unrelated writes. Editing an older card requires bringing its values into compliance before saving. These validation rules do not replace encryption or the opening credential.

Encrypted backups remain the default and require a dedicated export password entered once, a new salt, and a separate HKDF purpose label. There is no master-password export mode or stored backup password. The same export password is required to decrypt that file; fingerprints cannot substitute for a portable file's decryption password. Existing encrypted backup formats and their original passwords remain compatible.

The explicit **Export without encryption (no password)** checkbox instead creates a versioned, clearly marked unencrypted `.vault` document containing every saved card and note, including full card numbers, security codes, text, identifiers, and timestamps. It contains no master password, session keys, or editor drafts, but has **no confidentiality or cryptographic authenticity**. Anyone with access can read or modify its records. Import identifies this format without requesting a password; both formats are schema-validated and merged through the same encrypted local-write path. The local database remains encrypted regardless of export format.

Prepared exports and unencrypted import previews stay in volatile memory. **Save to files** writes directly to a user-selected document through Android's `ACTION_CREATE_DOCUMENT`, including Downloads, without broad storage access. Sharing either format writes an app-owned temporary file retained until the next cold launch because another app may read it after the chooser closes. This deliberately includes plaintext on disk when unencrypted sharing is selected. Cleanup only removes owned cache files; it cannot erase saved exports or recipient copies. JavaScript strings and files are not claimed to be securely erased.

**Backup files** tracks only files saved or explicitly selected by the user. The app retains Android's per-document read grant, not access to an entire folder or storage volume. The raw viewer requires the existing unlocked session but no fresh credential, and never derives a backup key or decrypts an encrypted file. Unencrypted backup text is visible as-is; encrypted envelopes remain ciphertext. Raw contents stay in component memory and within the existing secure window, are read with the same 12 MB bound as imports, and are not copied into the history database or an extra cache file. Opening a raw view does not import, modify, or authenticate the backup's records. An inaccessible or moved document must be selected again.

An authenticated snapshot can still be replayed by an attacker with full filesystem control; this local-storage design does not claim external rollback detection.

## Session and writes

Decrypted records exist in a non-persisted Zustand session. The payload key is held separately in a private volatile keyring. There is no session persistence or development-tools middleware.

Card/note editor drafts, including incomplete values, are held in the same volatile session with separate new-record and per-record keys. Form updates retain the latest values without persisting them. Back from the dedicated card page keeps its draft without writing; the full-screen note editor waits for successful encrypted persistence on Back/Done before returning to the collection. Empty new notes are not written, completely blank edits cannot replace existing notes, and discard/delete actions require confirmation. Successful saves and record deletion remove the applicable draft. Ending the session clears every draft; generation checks prevent late form or dismissal callbacks from repopulating cleared state. Drafts are excluded from encrypted snapshot serialization and backups. Authentication and backup-password inputs are not cached in this draft store.

The master password or optional fingerprint is required when opening a closed app. Ordinary backgrounding, inactivity, Android focus loss, file selection, and sharing do not end an unlocked session. Decrypted data, drafts, and the payload key remain in process memory during those transitions. The native shield still obscures the window and clipboard cleanup still runs. This deliberately trades automatic background locking for an uninterrupted session.

Android Back at the navigation root clears the session before exiting. Activity destruction outside configuration changes also clears a retained JavaScript session. Native activity-session tracking invalidates retained state before revealing a reopened activity even if Android did not deliver the destruction event to JavaScript. Process death naturally discards the session. Ending the session invalidates its generation, clears the keyring/snapshot/drafts, and unmounts sensitive navigation and editors. A later cold launch must unlock the encrypted vault again. An operating-system background-process eviction also requires unlocking on the next launch.

Creating, editing, or deleting a card/note, changing ordinary in-session settings, and merging an import do not require additional password or fingerprint confirmation. Enabling fingerprint unlock is the exception: Android authenticates protected-key setup, without another master-password entry. Destructive actions retain a non-credential confirmation. Service writes still require an unlocked session and remain serialized, encrypted before persistence, revision-checked, and transactionally committed. A generation change prevents pending work from updating a later session.

## Biometric storage

Biometrics are off by default and are used for app opening and protected-key enrollment. SecureStore protects the exported payload key with an Android Keystore AES wrapping key that requires authentication for each operation. The native adapter inspects the actual SecureStore key alias for hardware protection and authentication policy. It fails closed if those properties cannot be verified. A biometric unlock performs an authentication-bound SecureStore read, rather than trusting a separate biometric-success boolean.

Fingerprint enrollment is controlled by the **Settings > Security > Fingerprint unlock** switch inside an already-unlocked session, not by the opening screen. Enabling copies the current session's payload key into a temporary buffer for the existing authenticated SecureStore enrollment flow, then wipes that temporary buffer without clearing the active session key. It does not re-enter or retain the master password. Enrollment and hardware/per-use-authentication checks must complete before fingerprint unlock is marked enabled. Turning the switch off removes the wrapped key and disables the preference without changing vault ciphertext. Capability checks refresh when returning from Android settings, and an unavailable device can still turn an existing enrollment off. The opening screen retains fingerprint sign-in when enabled and master-password sign-in as the fallback.

The alias adapter is pinned to expo-secure-store 58.0.2 and must be revalidated during an Expo upgrade. Unsupported devices remain password-only.

Per-use inspection accounts for both legacy `KeyInfo`'s `-1` validity and modern Keystore2's zero timeout representation. On Android 11+, the key must explicitly authorize only `AUTH_BIOMETRIC_STRONG`; credential-only, mixed credential/biometric, unknown-authenticator, and positive timed-validity policies are rejected. Hardware-backed key storage and hardware-enforced authentication remain separate mandatory checks. Compatibility with the zero representation does not allow software-backed or unauthenticated keys. Failed setup removes only the attempted wrapped unlock entry, not vault records, and leaves master-password access intact.

Android can report biometric success before the system prompt has released window focus. The shared biometric wrapper waits for the actual active/focused state before returning an authenticated result, rather than delaying for a fixed sleep or bypassing the unlock foreground check. Focus/state events and the session generation are observed for at most three seconds; real backgrounding, session invalidation, a native focus-query failure, or timeout rejects the operation and removes its listeners/timer. The single-prompt guard remains held through this handoff. The final session-opening foreground/generation checks and key-buffer cleanup remain in force.

The wrapped vault key is not itself a non-exportable Keystore key: it must enter application memory to decrypt the vault. Root and password-verification keys are not stored alongside it. Enrollment invalidation/cancellation does not delete the vault.

## Android leakage controls

- FLAG_SECURE is installed at activity startup, before the React surface loads.
- expo-screen-capture also blocks capture at the application root.
- A native opaque shield covers the activity on pause/focus loss without waiting for JavaScript.
- Sensitive clipboard entries are flagged and cleared by a native ownership-aware timer/lifecycle guard.
- Sensitive text fields disable correction, spellcheck, autofill, autocomplete, and unrestricted context menus. The native activity applies IME_FLAG_NO_PERSONALIZED_LEARNING to its editable views.
- Internet access is permitted for the optional HTTPS BIN lookup and Google Play services' on-demand OCR setup; network-state/Wi-Fi-state permissions remain blocked, cleartext traffic is disabled, and Android cloud/device-transfer backups are excluded.
- All JavaScript, icons, and fonts are embedded. Cardvault configures no application analytics or remote crash-reporting service. Google ML Kit's own SDK metrics policy is described below.

Expo SDK 58's screen-capture module registers an Android capture observer during native initialization. Its normal DETECT_SCREEN_CAPTURE permission is retained because removing it causes a native startup abort, even when the app only requests capture prevention. READ_MEDIA_IMAGES is explicitly removed; no photo-library permission is requested. This permission does not grant network access or access to screenshot files.

## Explicit limits

This is application-level zero-knowledge storage, not protection against a compromised operating system.

JavaScript strings, React/runtime copies, and native crypto handles cannot be provably zeroized. Buffer overwriting and reference removal are best effort; no forensic RAM-erasure claim is made.

Process death can prevent application timers from firing. Clipboard cleanup is attempted earlier on lifecycle loss, retained for retry when Android denies access, and retried on foreground restoration. Cardvault cannot erase copies already made by a keyboard, accessibility service, clipboard manager, or another application.

Returning from another app or unlocking the Android screen does not ask for a new Cardvault credential while its session remains alive. Anyone who can access that unlocked app session can read, change, delete, or export its records; choosing an export password encrypts the backup but does not reverify the master password. Selecting unencrypted export deliberately removes the portable file's password protection, not the local vault's encryption.

FLAG_SECURE cannot block an external camera, a rooted OS, or every manufacturer bug. Physical-device verification remains necessary, particularly for biometric enrollment invalidation and lifecycle/screen-recording behavior. An emulator does not prove hardware-backed key protection.

Saving or sharing backup files and choosing a document provider delegates to applications with their own network permissions. Cardvault also permits internet access for the explicit card-entry lookup described below; it is no longer a network-permission-free app.

## Optional BIN lookup

When configured with a HandyAPI **Publishable (Frontend)** key, the card editor debounces new BIN input and sends exactly the first eight numeric digits to `https://data.handyapi.com/bin/<BIN>`. The client rejects complete PANs as lookup arguments and does not transmit cardholder data, the full card number, CVV, expiry, notes, vault identifiers, snapshots or encryption keys. HandyAPI receives the BIN, public API key and network address; its handling of those requests is outside Cardvault's local encryption model.

The build-time `EXPO_PUBLIC_HANDY_API_KEY` value is bundled publicly into the app; [configuration details](./nerdy.md#card-led-entry-and-optional-api-auto-fill) cover GitHub Actions and ignored local settings. It must not be a backend/secret key. API quota restrictions must be suitable for native clients; this app does not spoof browser headers to bypass restrictions. No lookup occurs without configuration, when merely opening a saved card/draft, or outside the active editor session. Pending lookups are cancelled on number changes, editor closure or saving, and stale/session-invalid results cannot overwrite form values. Manually edited fields are protected unless the user explicitly reapplies detected suggestions.

Only `Status: SUCCESS` replies supply suggestions. Available string values from Issuer, Scheme, CardTier, Type and Country.Name are copied as returned; a missing or unreadable field leaves its current value untouched and produces inline guidance. Non-successful/malformed replies, timeouts, missing keys and API errors do not change current entries. No fallback bank/network/type/tier/country is guessed. Manual corrections remain protected unless explicitly replaced with **Use API details**. Type, tier and country remain optional for legacy snapshots/backups, and saved metadata follows the ordinary encrypted write path. Luhn and the other Country codes are ignored. Lookup data is held only in the editor's memory, not persisted as a separate request history or sent to analytics.

The full-page card editor, live card preview, inline brand marks, options menu and month/year expiry picker stay within the existing secure application window. The preview uses the same artwork as the homepage, displays current full number/CVV values, and has no active copy/actions/gestures. Empty-field placeholders are display-only and never enter saved records or drafts. The picker does not create an unprotected native content modal. Its cancellation cannot alter expiry; current/future-month checks still run at save time. API status is persistent in-window text/preview data, not a native alert or a toast containing record details.

Home and editor card artwork deliberately display full card numbers and CVVs while unlocked; keep the screen private. Home accessibility labels retain only the last four number digits; preview number labels are generic and do not announce partial or full entered digits. The CVV and decorative bank watermark are excluded from accessibility trees in both views. **Copy details** places only the bank, name on card, number, expiry and CVV on the existing sensitive, expiring clipboard; it is not an encrypted backup.

## Camera and NFC card entry

The readers require the existing unlocked session and run only after an explicit **Scan card** or **NFC** action. Camera preview and the editable review stay within the secure main window. The native camera uses a TextureView-compatible preview, closes on lifecycle/window-focus loss or view removal, and drops old frames instead of accumulating images. No ImageCapture/video recording, gallery access, microphone permission, photo file, or card-image upload is used. Raw camera frames and bounded recognized text exist only in memory. A uniquely Luhn-plausible number must agree in three of the last five observations, including the current frame; expiry/name are confirmed independently from repeated observations of that number. Up to two common OCR character substitutions are permitted only within these candidate checks, not as arbitrary digit guessing. Ambiguous numbers are not selected, and uncertain fields stay editable. Detection remains fallible, and number, expiry, and holder can all be corrected before acceptance. Refocus/light controls do not save images, and the light is released with the camera.

Word geometry is used to reconstruct common stacked/wrapped layouts, excluding masked and CVV/security-code-labelled lines from numeric grouping, including split security-code labels. Bounded grayscale contrast and decorative-rule suppression can improve faint text; original frames remain available and no checksum rule is weakened. Each image mode must independently confirm the number. Temporary image/working arrays stay in memory and are cleared after processing, with the same best-effort erasure limitations as other runtime copies. Optional, developer-enabled scanner diagnostics contain redacted metrics and geometry only, not OCR text, recognized card values, or images.

OCR uses the unbundled Google Play services ML Kit Latin recognizer, downloaded on demand to retain the APK-size limit. An installed model can run locally without a network connection, but first use, model removal, or required Play services updates can prevent scanning until setup succeeds. Preparing/downloading/error states and manual entry are explicit. [Google's ML Kit policy](https://developers.google.com/ml-kit/terms) says input images and recognition outputs are processed on-device, while SDK performance/utilization metrics and model/service update traffic may contact Google. This is not a network-isolated or telemetry-free scanner.

NFC is optional hardware. The reader uses foreground ISO-DEP access and bounded EMV selection/processing-options/record-reading commands (including bounded response continuations). It never sends payment-authorization, PIN-verification, payment-cryptogram, or card-write commands. Parsing bounds response lengths, nesting, record ranges, terminal-data requests, request count, and elapsed reading time. Only number, available expiry, and available holder reach the review UI; raw NFC responses are not logged, exported, or persisted. Printed CVV is not read. A card can omit data, reject this flow, or return a number different from the one expected (particularly a wallet token); users must check the physical card, and unsupported cases require camera/manual entry. NFC does not establish card ownership or bank approval.

Leaving the reader, losing app/window focus, or ending a session cancels its native work. Request identifiers, mounted-state checks, and session generations discard late camera/NFC callbacks. Review is volatile; Cancel cannot change the card-addition draft. **Use details** validates the edited fields and returns to the editor, preserving the manually entered CVV. Only then is a fresh lookup requested using the corrected first eight digits, even when that BIN matches the previous lookup. No full PAN, image, expiry, name, or CVV goes to HandyAPI. No card is persisted until the existing encrypted **Save card** path succeeds.

The explicit **Share card details** action is different from encrypted backup export: it hands the bank, network, cardholder, complete card number, expiry, and CVV/security code to the operating system as plain text. It opens the native app chooser without additional confirmation or authentication, by user-requested policy. Card gestures only open the actions menu; they do not initiate sharing. Cardvault does not write this share text to a file or automatically copy it to the clipboard. Once a recipient app receives it, Cardvault's encryption, clipboard expiry, and screen-capture controls cannot protect or revoke that copy.

The explicit **Share note** action similarly sends only the title/body as plain text through the native app chooser. **Copy note** uses the existing sensitive, ownership-aware expiring clipboard. Neither action runs automatically when opening or editing a note. The note composer, action menus, and themed card/note deletion/discard confirmations remain inside the existing secure application window rather than opening an unprotected native content modal. Confirmation previews show only a card's bank/network/last four digits or a note's title and bounded text excerpt; full card numbers and CVVs are not included. The overlay blocks interaction/accessibility behind it, and cancellation cannot interrupt a pending encrypted mutation.

Card draft auto-fill ownership stores only field-name flags alongside the volatile draft, not API keys or another lookup history. Those flags are copied defensively, cleared with the session, and excluded from snapshots/backups.

No third-party security audit or PCI compliance certification is claimed. There is no cloud recovery, password escrow, or backdoor. Maintain independent encrypted backups and a safe record of the master passphrase.
